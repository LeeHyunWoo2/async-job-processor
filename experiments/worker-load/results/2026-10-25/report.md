# Worker 수에 따른 실측 결과

2026-10-25에 1·2·4·8 Worker × 두 번, 조건마다 `slow(durationMs=1000)` 480개를 실제 실행했다. 서로 다른 3,840개 Job 모두 첫 시도에 성공했고 Retry·Recovery·Crash는 관측되지 않았다. 아래 `유효`는 이 실행 조건을 통과했다는 뜻이다.

경과 초 = (마지막 성공 updatedAt − 첫 processingStartedAt) / 1000. PostgreSQL timestamptz를 UTC 밀리초로 변환한다.
Job/s = 이번 Batch 성공 수 / 경과 초. Speedup = N Worker Job/s / 1 Worker Job/s. Efficiency = Speedup / N × 100.
표준편차는 실제 반복 집합의 모집단 표준편차이며, 적은 반복의 범위·산포를 표시할 뿐 성능 신뢰구간이 아니다.

Prometheus는 Worker별 rate()를 구한 뒤 합산한다. Counter reset·Scrape 누락·2분 창의 구간 밖 값 때문에 DB Batch 완료 수와 처리량을 대체하지 않는다.
Handler Histogram은 Handler 호출~종료만 포함한다. DB 저장 시간·전체 Job 시간은 제외한다. Processing Gauge는 DB 상태이며 실행 Handler 수와 항상 같지는 않다.
Timer 기반 slow의 관찰값이다. Connection 증가만으로 PostgreSQL 병목을 단정할 수 없으며 병목 원인은 별도 증거가 없으면 원인 미확정이다.

## 환경과 실행 조건

- WSL2 Linux `6.18.54.1-microsoft-standard-WSL2`, Docker Desktop Engine `29.8.2`, Compose `5.5.1`, Node.js `24.21.0`.
- CPU 모델은 Intel Core i7-7700K @ 4.20GHz이며 WSL/Docker에 노출된 논리 CPU는 8개, 메모리는 8,329,564,160 bytes(약 7.76GiB)다. Windows Host의 전체 RAM은 별도로 측정하지 않았다.
- API·Worker는 같은 애플리케이션 이미지, PostgreSQL은 `postgres:18.6-alpine`, Prometheus는 `v3.13.4`를 사용했다. 개별 컨테이너의 CPU quota·cpuset·메모리 제한은 미설정이며 Docker 환경 전체 한도와 구분한다. 실제 이미지 ID와 Worker별 제한값은 JSON에 있다.
- Worker는 프로세스당 한 Job씩 실행하며 기존 Pool 설정을 유지했다. idle polling 1초, Recovery 검사 약 10초, Stale Timeout 30초다. DB `max_connections=100`, `shared_buffers=128MiB`, `work_mem=4MiB`다.
- 준비 트랜잭션이 이번 Batch의 행만 잠근 상태에서 Worker·Target 수와 최초 Scrape, Ready 480개를 확인했다. 준비 시간은 13.391~28.359초였고 DB 처리 구간에는 포함하지 않았다.
- DB 상태·자원·연결은 기본 5초 간격으로 관찰했고, API Gauge Scrape와 Worker Scrape·DNS 갱신은 기존 15초 간격이다. 자원 수집 376회 중 오류는 0회였으며 경계 밖 샘플을 제외한 355회를 집계했다. 수집된 모든 Target 스냅샷에서 해당 Worker 수와 `up` 상태가 일치했다. 샘플 사이의 일시적인 상태까지 보장하지는 않는다.
- 기본 조건 시작 당시 전용 DB에는 소규모 실행의 완료 행 24개가 있었다. 이번 Batch에 포함하지 않았고, 반복 사이에도 기존 행을 삭제하지 않았다. 테이블 증가·캐시·GC·실행 순서·Host의 다른 활동은 통제하지 않았다.
- 전체 Batch 처리 구간은 **2026-10-25 18:46:48.532~19:24:04.000 KST**(09:46:48.532~10:24:04.000 UTC) 안에 있다. 개별 시작·종료는 `summary.json`·`observations.json`에 보존했다.

실제 기본 실행 명령은 다음과 같다. 애플리케이션 소스·Schema·Metric 정의·의존성은 수정하지 않았다. 측정 당시 기준 commit과 도구의 SHA-256은 환경 자료에 남아 있다.

```bash
docker compose build
node --env-file=.env experiments/worker-load/run.ts \
  --out=artifacts/worker-load/2026-10-25-default
```

## 관찰과 확인하지 못한 원인

두 반복 모두 Worker 수 증가에 따라 DB 기준 처리량이 증가했다. 전체 Worker 메모리 중앙값은 1개에서 약 45MiB, 8개에서 약 467~471MiB였고 DB 연결 중앙값은 4→5→7→11개였다. Worker CPU 중앙값의 합은 1개에서 0.16~0.20%, 8개에서 1.62~1.75%였다. 이 CPU 비율은 논리 CPU 하나를 100%로 보는 Docker 값이다. PostgreSQL CPU 중앙값은 0.36~4.18%, 최대 관측값은 8.88%였다.

이 샘플에서 CPU 포화나 Worker 증가에 따른 처리량 정체를 확인하지 못했다. 쿼리별 시간·DB wait·I/O 원인 분석은 수행하지 않았으므로 **병목 원인 미확정**이다. 연결 증가를 PostgreSQL 병목의 증거로 사용하지 않는다. 2 Worker의 중앙값 기준 Efficiency 100.2352%는 실제 산식의 결과이며 100%로 제한하지 않았다. 적은 반복과 시각 변동이 있는 환경에서 이를 특별한 최적화 효과로 해석하지 않는다.

Handler 평균은 실행별 1.00058~1.00067초였지만 Job별 DB Claim→성공 시각 차이는 0.525~4.211초였다. 별도 Node.js 관찰 프로세스에서 5초 간격으로 `Date.now()`와 `performance.now()`의 누적 경과 차이를 기록했다.

| 시각 관찰 파일 | 샘플 | wall clock 경과 초 | monotonic 경과 초 | 누적 차이 변화 초 |
|---|---:|---:|---:|---:|
| clock-check.jsonl | 25 | 131.000 | 120.086 | +10.914 |
| clock-check-continued.jsonl | 351 | 1908.140 | 1749.924 | +158.216 |

첫 관찰에서 연속 샘플 사이 차이 변화는 약 −0.454~+3.181초였다. 이 시각 변동의 발생 원인과 각 Batch 결과에 미친 정확한 영향은 확인하지 못했다. DB 시간에서 Handler 시간을 빼서 DB 오버헤드를 추정하거나 측정값을 임의로 보정하지 않는다. 이 자료만으로 병목·최적 Worker 개수·포트폴리오 결론을 확정하지 않는다.

Prometheus에서는 Ready Queue 480개가 감소하고 Processing Gauge의 관측 최대가 각 조건의 1·2·4·8이었다. `r1-w1`·`r2-w2`의 저장된 Queue 시계열 마지막 값은 각각 2·4다. 마지막 5초 평가 격자가 실제 마지막 Scrape보다 앞선 경우이며 DB 대상 Job은 전부 성공했다. 원자료를 수정해 0을 채워 넣지 않았다.

`r2-w1` 시작 부근의 `sum(rate(...[2m]))`는 최대 약 4.6518 Job/s였고 이전 8 Worker의 instance 시계열이 함께 남아 있었다. 해당 Batch의 DB 처리량은 0.9083 Job/s다. 이처럼 이전 실행·Counter reset·짧은 창이 섞인 rate를 최종 Batch 처리량으로 사용하지 않는다.

## 자료와 검증 범위

버전 관리 대상으로 이 보고서·요약 JSON·관찰 요약·CSV만 선별했다. 원본 Job ID·DB 행·로그·복수 자원 샘플·Prometheus 시계열·시각 관찰 JSONL은 Git에서 제외한 `artifacts/worker-load/2026-10-25-default/`에 보존했다. Named Volume도 유지하며, 기존 개발용 데이터와 분리한 실험 컨테이너·Network는 정리했다.

실행 흐름 확인용 `artifacts/worker-load/smoke/`는 별도 자료다. 12 Job·500ms·1/2 Worker 조건이며 짧아서 구간 내 자원 샘플이 없었다. 기본 비교에는 포함하지 않았다. 기본 조건 8회는 모두 완료했으며 정상 비교에서 제외된 Batch는 없다. 10~50ms 추가 실험·세 번째 반복·CPU-heavy 실험은 수행하지 않았다.

- `npm run typecheck`, `npm run test:observability`(5개), `npm run test:db`(49개) 통과.
- 집계 산식·Retry/누락/다른 Batch 거부·반복 기준 검증 3개와 실제 Ready·Stale 잔여 Job의 사전 거부·행 보존 검증 1개 통과.
- `npm run test:multi-worker`의 정상 분담·SIGKILL 이후 Recovery·Scale 변경과 SIGTERM, Prometheus 개별 수집 시나리오 통과.
- 실제 기본 실험에서 모든 ID의 준비 상태·최종 성공·attempt=1, Worker별 단일 Claim·성공 로그, 프로세스 유지, 마지막 성공 Counter·Handler 관측 수와 DB 완료 수 일치를 확인했다.

재실행 절차·처리 구간 산식·자원 단위·실패 시 보존과 정리는 [실험 안내](../../README.md)를 따른다. 최종 기술적 해석과 포트폴리오 결론은 사용자와 ChatGPT가 별도로 판단한다.
