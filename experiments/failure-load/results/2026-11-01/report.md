# Failure / Load 리뷰 보완 검증 — 2026-11-01

장애 후 처리 증거와 정상 대조군 적합성 판정을 보강했다. 요청별 원자료 수집은 유지하면서 RTT·완료율·Stale 기준 집계를 보완했다. 이 기록은 작은 도구 검증 결과이며 PR 2의 실제 Pilot이나 120초 기본 4회 실측 결과가 아니다. [사용법](../../README.md)과 [선별 수치·코드 Hash](summary.json)를 함께 확인한다. [10월 31일 기록](../2026-10-31/report.md)은 당시 판정 기준의 검증 자료로 보존했다.

## 반영 사항

- 생존 처리 증거는 SIGKILL 확인 후 발송해 201로 수락된 일반 Job만 사용한다. 성공 로그의 Worker UUID·컨테이너가 확인된 생존 Worker에 해당하고, 성공 행의 DB 소유권이 같아야 한다. 성공 행을 조회한 뒤 대상이 여전히 최초 Claim의 첫 processing에 남아 있는지 다시 조회한다. `evaluate()`도 이 근거를 재검증하므로 관측 마커의 존재만으로 통과하지 않는다.
- `--purpose=main|pilot|smoke`를 구분했다. 정상 3개 Worker는 대상 완료 후 10초 구간 2개 연속 503, 또는 3구간 연속 outstanding 평균 증가와 첫·끝 평균 차이 3개 이상을 부적합으로 본다. 위반이 없더라도 온전한 구간 3개와 각 구간의 요청·DB 표본이 부족하면 판단 보류다. 이 기준은 사용자 확인 후 적용했다.
- main의 정상 3개가 부적합·판단 보류이면 시나리오 미성립으로 처리한다. Pilot 3개는 관측 자체의 유효성과 본 실측 적합성을 분리한다. 두 경우 모두 `requiresUserDecision=true`, exit code 1로 종료하고 다음 반복을 실행하지 않는다. Worker 2개 Pilot의 의도된 과부하와 작은 Smoke에는 정상 3개 기준을 강제하지 않는다.
- `rttMsByOutcome`에 수락 201·정책 거부 503·기타 HTTP·네트워크/본문 오류 분포를 분리했다. 기존 `rttMs`는 혼합 분포로 유지한다. 단계별 완료 필드는 `logObservedCompleted*`로 명시하고, 단계 내부 DB 표본의 성공 수 변화·같은 관측 구간의 성공 로그 수·차이를 함께 기록한다. 최종 전체 DB 성공 수 변화와 전체 성공 로그 수도 대조한다.
- Recovery 확인 시 DB 기준 최초 Claim 경과가 30초 미만이면 기능 위반, 값이 없으면 근거 부족으로 판정한다. 확인 시각의 경과가 충분하다는 사실과 Recovery 트랜잭션의 정확한 발생 시각은 구분한다.
- 날짜별 `results/YYYY-MM-DD/report.md`·`summary.json`만 Git 추적 예외로 허용했다. PR 2 결과 날짜도 같은 규칙을 사용하며 요청·자원 원자료는 계속 제외한다.

## 실제 Compose 근거

원자료는 `artifacts/failure-load/smoke-1793459290363/`에 있다. Node.js v24.21.0, Docker 29.8.2, Compose 5.5.1과 기존 전용 이미지를 사용했다. API·Worker의 실제 소스/이미지 대조에 더해 이번 실행의 도구·테스트 Hash가 최종 파일과 일치하는 것도 확인했다.

정상/장애 Smoke는 `purpose=smoke`, Worker 3개, 일반 6 jobs/s × 12초, 별도 대상 1개, 상한 8로 실행했다. 정상은 일반 72개 중 수락 30·거부 42, 장애는 수락 31·거부 41이었다. 대상은 각각 1개 수락됐고 정상 attempt=1, 장애 attempt=2로 성공했다. 양쪽 관측 최대 미완료는 8이었다. 이 의도적 과부하 조건은 `observation-only`이며 정상 3개 본 실험의 부하 적합성을 인증하지 않는다.

장애 조건의 강화된 증거는 다음과 같다. 시각은 모두 실행기의 생산 시작 기준 Monotonic 관측 경과다.

| 사건 | 관측 경과 |
|---|---|
| SIGKILL 종료·생존 2개 확인 | 약 3.268초 |
| 증거로 선택한 일반 요청 발송 | 약 3.500초 |
| 해당 요청 201 수락 확인 | 약 3.506초 |
| 생존 Worker의 성공 로그 수신 | 약 6.801초 |
| 성공 DB 행·대상 첫 processing 잔류 확인 | 약 6.863초 |

이 요청은 SIGKILL 확인 이후에 발송됐으므로 장애 전에 존재하던 Job의 지연 로그로 설명할 수 없다. 이후 자연 Recovery·두 번째 Claim·대상 성공을 확인했다. Recovery 확인 시 DB 기준 최초 Claim 경과는 약 32.357초였다. 정상과 장애의 최종 전체 DB 성공 수 변화/로그 성공 수는 각각 31/31, 32/32였다. 표본 2개 이상이 있었던 단계 내부 비교에서도 차이가 0이었으며, 짧은 단계는 비교 불가로 남겼다. 이는 다른 환경에서도 로그 지연이 항상 없다는 보장은 아니다.

별도로 `purpose=main`, 12초의 짧은 정상/장애 순서를 요청해 진행 차단을 확인했다. 정상의 기능·측정·정리는 통과했지만 대상 완료 후 안정성 관측 구간이 부족해 `inconclusive`, `requiresUserDecision=true`가 됐다. 정상 결과 1개만 저장되고 다음 장애 반복은 실행되지 않았다. 이는 부적합한 부하를 확정하는 Pilot 결과가 아니라 관측 부족과 사용자 판단 경로의 검증이다.

기존 미완료 Job 사전 거부·전체 기존 행 보존·다른 컨테이너 상태 유지도 통과했다. 실제 로그/결과 파일 저장 실패에서는 측정과 반복 정리 실패를 분리하면서 후속 환경 정리를 완료했다. SIGTERM에서는 요청 정산·미발송·잔여 queued·로그를 보존하고 전용 컨테이너만 종료했다. Smoke가 생성한 fixture만 ID로 한정해 정리했고 기존 행·볼륨은 유지했다.

단위 검증은 장애 전 요청의 늦은 성공 로그 거부, 실제 장애 후 요청 수락, 생존 소유권·대상 상태 불일치 거부를 포함한다. 안정성에서는 지속 503·증가 추세·구간 부족·일시적 503·작은 변동·대상 실행 과도 구간을 구분하고 Pilot 2개/3개와 Smoke의 적합성을 확인했다. 201=100ms·503=5ms fixture로 혼합 RTT가 낮아져도 수락 RTT가 별도로 유지됨을 확인했고, 로그 지연에 따른 DB/로그 완료량 차이를 보정하지 않고 드러내는 것도 검증했다.

정상 3개의 충분한 실제 안정성 관측, Worker 2·3개 Pilot, 후보 유입률 판단과 120초 기본 실측은 PR 2에 남아 있다. 현재 부하 설계의 적합성을 새로 확정한 결과는 없다.
